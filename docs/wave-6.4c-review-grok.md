# Wave 6.4C review — offscreen OAuth popup adoption

**Verdict: FIX-THEN-MERGE.**

Commit `c0455f42c` (`luminor/preserve-gpui-oauth-popups` vs `5acaa574d`) does the load-bearing thing correctly: offscreen `window.open` classified as `popup` is `allow`ed with a hidden offscreen option bag, and `did-create-window` adopts that Electron-created `webContents` as the live pane tab instead of `deny` + `loadURL` into a new runtime. The attached ADE path still returns `allow` + `buildOAuthPopupWindowOptions(this.window)`, `target=_blank`/kind `tab` still denies, `about:blank` still classifies as popup in `classifyBrowserWindowOpen`, popup close/restore for the four listed paths is reentrancy-safe, and `enforceBackgroundAutomationRuntimeBudget` now pins the opener and the child. That is not enough to merge. Adopting the popup as `activeTabId` creates a second live offscreen runtime whose opener is now inactive, and two existing destroy paths were not updated: `closeTab` on the opener snapshots `nextTabs` before `closePopupWindowsForTab` mutates the list and then writes the dead popup tab back, and `suspendInactiveTabs` / `suspendThread` still destroy opener runtimes that the budget path now protects. Both can replace the OAuth document with a fresh `BrowserWindow` and sever `window.opener`. No IME, DnD, or multi-viewer code is in the diff.

## Findings

1. **MAJOR — `closeTab` on an opener resurrects the destroyed popup tab and can construct a new document.** `apps/desktop/src/browserManager.ts:2109` captures `nextTabs` before any popup teardown. Closing the popup itself takes the `findAdoptedPopupRuntime` early return at `:2114` and is fine. Closing the opener (or any ancestor that is not itself an adopted popup) falls through to `:2120` `closePopupWindowsForTab`, which correctly destroys descendants via `removeAdoptedPopupTab` (`state.tabs` becomes `[opener]`, `activeTabId` restored). `:2125` then assigns the stale snapshot (`[popup]`). `:2141-2147` makes the ghost popup active and `attachActiveTab` / the frame controller's tab-switch `activateRemoteRuntime` will `ensureLiveRuntime` a **new** offscreen window and `loadTab` the provider URL — hunt item 1's failure mode, reached through close rather than through the allow handler. `closeAutomationTab` (`:1660-1682`) filters `state.tabs` *after* popup teardown and does not have this bug. **Fix:** do not reuse a pre-teardown `nextTabs` after `closePopupWindowsForTab`. Filter after popup close, or return through the same path `closeAutomationTab` uses. Add a test that closes the source tab while the adopted popup is live and asserts the popup tab/runtime are gone and no second `BrowserWindow` is constructed for the popup URL.

2. **MAJOR — opener (and chain) are still destroyed by inactive-tab suspend, which this PR newly makes reachable.** Eviction via `enforceBackgroundAutomationRuntimeBudget` (`:2379-2393`) now keeps `[popup.tabId, popup.openerTabId]`. `suspendInactiveTabs` (`:2445-2486`), `scheduleInactiveTabSuspend` (`:2544-2569`, 1.5s / 400ms), and `suspendThread` (`:2509-2525`) were not taught the same set. Adopting a popup sets `state.activeTabId` to the child (`:1200-1201`), so the opener is an inactive live runtime. `BROWSER_MAX_WARM_INACTIVE_RUNTIMES_PER_THREAD` is 1: the opener is scheduled for destroy, and any extra inactive ancestor is destroyed immediately. `attachActiveTab` (`:2594`) and `resumeThread` (`:2319`) both call this. GPUI streaming itself uses `activateRemoteRuntime` (no suspend), but the Electron shell still calls `setPanelBounds` → `attachActiveTab` whenever the in-app panel is mounted for the same thread, and `suspendThread` still destroys every non-`automationRuntimeKeys` tab — including a human GPUI popup, which is never added to `automationRuntimeKeys`. The new eviction test (`browserManagerAutomation.test.ts` "does not evict an offscreen opener while its adopted popup is live") never advances the suspend timers and never calls `setPanelBounds`. **Fix:** skip `popupOwnerRuntimeKeys` (full ancestor chain, not only immediate opener) in `suspendInactiveTabs` and `suspendThread`, the same way the budget path does. Cover it with fake timers + `setPanelBounds` / `resumeThread` while a popup is live.

3. **MINOR — `activateRemoteRuntime` can still `loadURL` the adopted child when `getURL()` has not caught up to `details.url`.** `apps/desktop/src/browserManager.ts:555-557` force-loads whenever `currentUrl` is empty or disagrees with `tab.lastCommittedUrl ?? tab.url`. Adoption stores the `did-create-window` URL on the tab (`:1171`) and reuses `popup.webContents` (`:1180`), which is correct, and the new test asserts `childContents.loadURL` is not called **when `getURL()` already equals that URL**. At `did-create-window` time Chromium often still reports `""` or `about:blank` while the handler URL is the provider authorize endpoint. A tab-switch `activateRemoteRuntime` would then `loadTab({ force: true })` on the same `webContents`. That is not a second runtime, so `window.opener` usually survives, but it cancels the in-flight `window.open` navigation and can fight OAuth SDKs that open `about:blank` and then assign `location`. **Fix:** if the active runtime is an adopted popup (`findAdoptedPopupRuntime` / `ownsWebContents` + `popupRuntimes`), skip this force-load and let Chromium own the child's navigation. Extend the adoption test with `getURL: () => ""` and `getURL: () => "about:blank"` against a provider URL.

4. **MINOR — offscreen agent `window.open` reports `openedTabId: null` and then becomes a canonical tab.** `apps/desktop/src/browserManager.ts:812-819` emits `kind: "popup", openedTabId: null` under an automation gesture, then `did-create-window` adopts the child as `activeTabId`. `desktopBrowserAutomationHost.reconcileWindowOpen` treats that event as `oauthPopup: true` and will not follow a tab. The attached ADE test ("reports an agent-opened OAuth popup without converting it into a tab") still passes because that runtime has no `placement: "offscreen"`. Human GPUI OAuth does not use this event. Agent-driven sign-in in the pane will stream a tab the tool does not know about. **Fix:** emit after adoption with the new tab id, or emit `kind: "tab"` once the child is canonical; keep `openedTabId: null` only on the attached native-popup path.

5. **MINOR — `about:blank` staging is not locked on the manager offscreen handler.** `packages/shared/src/browserSession.ts:169-172` still classifies `about:blank` as `popup` even with `frameName: "_blank"` and empty features, and `browserSession.test.ts` covers that. The new manager tests only allow Google/GitHub URLs *with features*, and deny `docs.example` `_blank`. An SDK `window.open("about:blank", "_blank")` therefore depends on the shared helper remaining wired, with no `DesktopBrowserManager` assertion that the offscreen handler `allow`s and adopts that child. **Fix:** one offscreen handler + `did-create-window` test with `url: "about:blank"`, empty features, `_blank`.

6. **MINOR — no post-create hide; tests never prove `centerPopupWindow` is skipped when a shell window exists.** Constructor options are `show: false`, `offscreen: true`, no `parent`, select-shim preload, `skipTaskbar: true` (`browserSessionPolicy.ts:175-192`, handler at `browserManager.ts:825-835`). `updatePopupWindowsForThread` (`:1357-1362`) skips centering when `openerTabId` is set. Offscreen automation tests never `setWindow`, so `centerPopupWindow` would no-op even without that skip (`:1335-1337` returns if `this.window` is null). If Electron's `window.open` child ignores `show: false` and the desktop shell window is set, a missed skip would `setBounds` against the visible parent and map an `xdg_toplevel`. **Fix:** `popup.hide()` in `adoptOffscreenOAuthPopupWindow` before any other window call; add an offscreen test that `setWindow`s a fake parent with `getBounds` and asserts the child never `setBounds` / `show`.

## Verified fine (do not re-litigate)

- **Same `webContents`, not a clone.** `adoptOffscreenOAuthPopupWindow` stores `popup.webContents` (`:1180`), `ensureLiveRuntime` returns the existing offscreen runtime (`:2720-2725`), and the adoption test asserts `activateRemoteRuntime` returns `childContents`, `browserWindowConstructor` was called once (the source pane), and `childContents.loadURL` was not called in the matching-URL case.
- **Offscreen option bag vs attached option bag.** Offscreen returns `buildOffscreenWindowOptions` only: `show: false`, `offscreen: true`, `backgroundThrottling: false`, `partition: persist:luminor-browser`, sandbox / contextIsolation / no Node, optional preload, `skipTaskbar: true`, no `parent`. Attached still returns `buildOAuthPopupWindowOptions(this.window)` (`:847-863`). `createLiveRuntime` (`:2772-2779`) now uses the same helper *without* `skipTaskbar`, so pane runtimes are not accidentally taskbar-hidden. `buildOAuthPopupWindowOptions` is unchanged.
- **Tab vs popup.** Offscreen `kind === "popup"` allows; any other kind still `deny`s and `scheduleWindowOpenTab`. Shared `classifyBrowserWindowOpen` is untouched: features → popup, reserved `_blank` without features → tab, known OAuth URLs → popup, `about:blank` → popup. Target-blank denial is tested on the manager.
- **Popup close / restore / descendants / reentrancy.** Pane tab, child `closed`, Escape, Ctrl-W all destroy the child, drop the tab, and restore the immediate opener. Chains close descendants (`closePopupWindowsForTab` matches `tabId` or `openerTabId`). `closePopupRuntime` (`:1291-1301`) drops the map entry before `destroy()`, so the `closed` listener is a no-op on reentry. Shared `listenerDisposers` between `LiveTabRuntime` and `OAuthPopupRuntime` is emptied once. Cmd-W (`input.meta`) is implemented; only Ctrl-W is tested.
- **Budget eviction.** `popupOwnerRuntimeKeys` includes each popup tab and its immediate opener, so A→B→C pins A, B, and C. The new test keeps the automation opener alive past the 31s grace while a fifth background runtime is evicted.
- **Streaming / generation / input.** Frame controller still generation-fences tab switches (`controller.ts:641-643` → `reconfigure(..., "tab-switch")` → `activateRemoteRuntime`). Acquisition binds `paint` / IPC / dialogs to the returned runtime `webContents`. Dialog monitor is started on the child (`:1185-1188`). Select-shim preload is the same `offscreenPreloadPath` `main.ts` already passes (`:370`).
- **Scope.** Diff is `browserManager.ts`, `browserSessionPolicy.ts`, three test files, and the author report. No IME, DnD, or multi-viewer.

## Tests vs the 88-count claim

The author report's 62 + 26 split matches the files: I counted 62 desktop cases (`it` + the 4-way `it.each`) across the four desktop files, plus 26 tests in `packages/shared/src/browserSession.test.ts`. I re-ran the shared file in this worktree: **26/26 passed**. The four desktop files could not be executed here (`Cannot find package 'effect'` / `@luminor/shared/...` from `apps/desktop`); this worktree does not have a complete workspace install. That is an environment gap, not a reason to distrust the case count.

The new tests are not "action: allow only." They assert child `webContents` identity, no second `BrowserWindow`, no `loadURL` on the happy path, exact offscreen option bags, attached `parent: mainWindow`, four close paths, chain teardown, and budget eviction of a *different* runtime. They still do not encode `window.opener` / `postMessage`, `about:blank` adoption, opener-tab close, or suspend-timer survival. Those are holes, not lies.

## Remaining live acceptance (out of this PR)

Even after the MAJORs above are fixed, merge does not prove Google or GitHub OAuth in a real GPUI pane. Confirm separately:

- Electron actually honors `offscreen: true` + `show: false` on `setWindowOpenHandler` children and fires `did-create-window` with that `webContents`.
- No visible Wayland toplevel and no native-widget SIGTRAP (`zxdg_exporter_v2`) while the popup is streamed.
- Real Google and GitHub callbacks `postMessage` to `window.opener` after pane interaction.
- The attached Electron ADE popup still appears parented and visible.

No GPUI crate change is required for this desktop slice once the two MAJORs are fixed: `activeTabId` selects the streamed child and `openerTabId` already exists on `BrowserTabStateSnapshot`.
